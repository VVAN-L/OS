**功能说明：**

### 功能模块：进程调度
**负责人：** 2412934-王海沛

#### 模块功能描述
**需要实现/修改的函数：**

```c
void cpu_idle(void);                              // kern/process/proc.c
void schedule(void);                              // kern/schedule/sched.c
void proc_run(struct proc_struct *proc);            // kern/process/proc.c
void switch_to(struct context *from,
               struct context *to);                // kern/process/switch.S
```

**功能说明：**

本模块负责将已经创建的内核线程交给 CPU 执行，完成从调度请求、线程选择到上下文切换的完整过程。

cpu_idle() 作为空闲线程的执行主体，持续检查当前线程的 need_resched 标志，并在需要重新调度时调用 schedule()。schedule() 遍历进程链表，选择处于 PROC_RUNNABLE 状态的线程，在没有可运行线程时选择 idleproc。

proc_run() 在关闭中断的临界区内更新 current，设置目标线程的 Sv39 页表，刷新 TLB，并调用 switch_to() 完成上下文切换。switch_to()根据 struct context 的布局保存旧线程的 ra、sp和 s0～s11，恢复目标线程的对应寄存器。

新线程首次执行时，通过预先设置的 context.ra 进入 forkret，随后沿 forkrets → __trapret 恢复链路进入内核线程入口。

### Challenge：

Q1：说明语句 local_intr_save(intr_flag); ... local_intr_restore(intr_flag); 是如何实现开关中断的。

A：两个宏通过控制 sstatus 寄存器中的 SIE 位实现开关中断。具体来说，local_intr_save(intr_flag) 保存 SIE 位并置 0，执行临界区代码，随后 local_intr_restore(intr_flag) 根据保存在 intr_flag 中的结果恢复 SIE 位。

Q2：get_pte() 函数中有两段形式类似的代码，结合 sv32、sv39、sv48 的异同，解释这两段代码为什么如此相像。

A：两段相似的代码分别是：

```c
pde_t *pdep1 = &pgdir[PDX1(la)];
if (!(*pdep1 & PTE_V)) {
    // 分配页表页、设置引用计数、清零，并写入 pdep1
}
```

```c
pde_t *pdep0 =
    &((pte_t *)KADDR(PDE_ADDR(*pdep1)))[PDX0(la)];
if (!(*pdep0 & PTE_V)) {
    // 分配页表页、设置引用计数、清零，并写入 pdep0
}
```

第一段代码的功能是通过 PDX1(la) 找到根页表中的表项，检查并按需创建下一级页表；第二段代码根据上一表项找到中间页表，再用 PDX0(la) 定位，检查并按需创建下一级页表。

两段相似是因为：Sv32、SV39、Sv48都是多级页表，页表各层结构相似，向下走一级所做的操作也相同。按照这种展开写法，Sv32 只需一段“定位或创建下一级页表”的逻辑，Sv39 需要两段，Sv48 则需要三段。

Q3：目前 get_pte() 函数将页表项查找和页表页分配合并在一个函数里，你认为这种写法好吗？有没有必要把两个功能拆开？

A：这样的写法是合理的，但在复杂系统下可能会产生问题。当前 get_pte() 通过参数 create 的值区分查找和分配两种行为。这样写的好处在于需要分配时能复用页表查找的逻辑进行遍历；但缺点是返回 NULL 既可能表示页表不存在也可能表示分配失败，且分配失败没有进行回滚。

## 六、实验总结与收获

### 对操作系统的理解

1. 列出你们认为本实验中重要的知识点，以及与对应的 OS 原理中的知识点，并简要说明二者的含义、关系和差异

（1）进程状态与调度选择
- 实验中的知识点
  schedule() 遍历进程链表，通过 PROC_RUNNABLE 状态判断线程是否可以获得 CPU。
- 对应的 OS 原理
  操作系统通过进程状态描述执行情况，调度器从就绪进程中选择下一个执行者。
- 联系与差异
  本实验使用 PROC_RUNNABLE 同时表示就绪和正在运行，通过 current 区分当前运行线程。OS 原理通常分别讨论就绪态和运行态。

（2）循环调度与 CPU 调度策略
- 实验中的知识点
  schedule() 从当前线程之后开始循环遍历链表，选择遇到的可运行线程。没有可运行线程时选择 idleproc。
- 对应的 OS 原理
  CPU 调度策略决定就绪进程获得 CPU 的顺序，影响公平性、响应时间和吞吐量。
- 联系与差异
  本实验实现了简单的循环选择机制。完整的时间片轮转调度还需要定时器触发抢占，其他调度算法则可能考虑优先级等因素。

（3）重调度标志与调度时机
- 实验中的知识点
  cpu_idle() 持续检查 need_resched，标志置位时调用 schedule()。
- 对应的 OS 原理
  调度请求可以先通过标志记录，再在适当的执行位置进行调度。
- 联系与差异
  本实验首次调度由初始化时设置的重调度标志触发。目前时钟中断尚未接入时间片抢占路径。

（4）寄存器保存与上下文切换
- 实验中的知识点
  switch_to() 保存旧线程的 ra、`sp`、`s0`～`s11`，并恢复目标线程的对应寄存器。
- 对应的 OS 原理
  上下文切换通过保存和恢复执行现场，使多个进程或线程能够交替使用 CPU。
- 联系与差异
  本实验根据 RISC-V 调用约定保存被调用者保存寄存器，并保存返回地址和栈指针。中断现场中的其他寄存器由中断帧恢复路径管理。

（5）临界区保护与原子性
- 实验中的知识点
  schedule() 和 proc_run() 使用 local_intr_save()、`local_intr_restore()` 保护关键操作。
- 对应的 OS 原理
  临界区保护用于避免共享状态在更新过程中受到并发执行的干扰。
- 联系与差异
  本实验通过关闭本地中断，避免单核上的中断打断调度与切换过程。多核系统还需要锁等同步机制协调其他 CPU 的访问。

（6）页表切换与地址空间
- 实验中的知识点
  proc_run() 将目标线程的页表物理地址写入 Sv39 格式的 satp，随后刷新 TLB。
- 对应的 OS 原理
  页表决定虚拟地址到物理地址的映射，TLB 缓存地址翻译结果。切换地址空间时需要维护二者的一致性。
- 联系与差异
  本实验中的内核线程共享内核地址空间。用户进程通常拥有独立地址空间，切换时需要使用各自的页表。

（7）首次运行与执行环境初始化
- 实验中的知识点
  新线程通过预先设置的 context.ra 进入 forkret，再沿 forkrets → __trapret 恢复中断帧，进入线程入口。
- 对应的 OS 原理
  新进程或线程需要在第一次获得 CPU 前建立初始执行环境，包括入口地址、栈和处理器状态。
- 联系与差异

### AI 协作开发的经验

通过本次协作，我们认识到，提示词需要明确函数接口、依赖条件、修改范围和验收标准。例如，明确要求使用 Sv39 satp，可以避免误用项目中遗留的 Sv32 接口。

AI 生成的底层代码需要结合结构体布局、调用约定和硬件执行流程检查。汇编中的寄存器偏移、临界区的中断状态恢复以及新线程首次运行的返回地址，都直接影响系统能否正确执行。

验证结果也需要准确记录。本次修改文件已经通过交叉编译，但完整构建和 QEMU 运行验证仍有待完成，因此报告只能确认已实现与已验证的部分。

在限制修改范围时，可以在 [PROMPT] 中要求“禁止修改已有函数实现”，同时明确是否允许补充前置声明。这样能够减少 AI 对其他模块的额外修改，并让最终改动更容易审核。
